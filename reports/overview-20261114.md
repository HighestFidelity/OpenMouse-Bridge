## 4. Missing / not thought of yet
- The fork goes "outdated" in the web app every Friday: it compares /v1/status version to upstream's GitHub latest
  by string (openmouse BridgeStatus.tsx:77); fork Cargo.toml is 1.0.0, upstream latest is 1.0.1 since 11-13.
  Real fix on our side = a weekly upstream sync routine (version tracks upstream). No API version on REST/WS either.
- #74 for every Attack Shark X11 user in every browser: the web app installs the Bridge HID shim with force:true
  whenever Bridge runs, Chrome included (main.tsx:54, "Prefer Bridge when it is installed"), and Bridge
  answers PUT /v1/native/settings 429 while any HID session is open (api.rs:461-466). Fix = session token, needs panel.
- Interface choice by capability: Bridge opens HID interfaces with no feature reports (keyboard-protocol #16, Desktop #28,
  mouse-protocol #99). hid.rs:1492 report_paths prefers declaring paths only inside one device.
- Battery tray polls by respawning the Node helper; Logitech goes stale that way (#170). Persistent HID++ listener
  with 0x1004 events + slow fallback poll + "last checked" is better.
- Safari has no path at all (mixed content); would need Bridge to serve the app over loopback. Big, upstream-level.
- API surface the web app never calls: /v1/custom-games (3 routes, image-from-url is attack surface), /v1/handshake,
  GET /v1/applications, DELETE /v1/battery/{id}, PUT /v1/autostart. [Unverified] Desktop and Bridge's own panel not
  checked for callers. Removal candidates only after that check (needs Victor + upstream).
- Stale web banner for old Bridges points Windows at the zip and Linux at curl|bash, not setup.exe/AppImage.
- install-linux.sh still points at upstream (open since 11-12, Victor's call).

- bridge-server.mjs: the fork deleted it as unused, but upstream still edits it (#62 02a2594). Recheck before
  PR-plan item 14 or resolving the sync conflict by deletion.

## 7. Opening the scope (cross-repo)
Bridge alone cannot finish F1 (true fix = persistent DPI in mouse-protocol for MX), F4 (panel UI for assignments),
F6/F7 (web app must send a token / read an api version), Safari (web app + Bridge static route).
Proposal: fork openmouse and mouse-protocol into HighestFidelity, same rules as this fork (offline builds/tests,
t3/<topic> worktrees, upstream PRs only on Victor's word). Order: Bridge first (F1, #120, sync), then web app for
F6/F7, then mouse-protocol for persistent DPI. keyboard-protocol, Desktop, docs, landing page: no reason yet.
Cost: openmouse is a big TS app (2944 stars, ~38 open items); needs Node/npm install on a box or PC (ask first).
